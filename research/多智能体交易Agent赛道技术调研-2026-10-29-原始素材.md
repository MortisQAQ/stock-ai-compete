# 多智能体交易 Agent 赛道：高星实现与技术原理调研

> 调研时间：2026-10-29 ｜ 方法：GitHub API 实测 star + 本地 12 个仓库源码逐行阅读 + 论文/榜单核对
> 命题：openOutcry 目前是"单 Agent 训练场"，要不要补上**多智能体团队协作**与**Agent 特定提示词**两件事？先看清别人怎么做的。
> 证据等级：★代码级 = 我读过源文件；☆文档级 = README / 论文 / 官网陈述

## 0. 结论速览（先看这 8 条）

1. **这条赛道上"多智能体"已经是默认形态，不是加分项。** 头部 118k★ 的 TradingAgents 就是 12 个角色 + 两轮辩论；A 股 fork 已经把角色扩到 7~15 个。openOutcry 若只保留"单 Agent 打分"，在评审视角里会被读成"评测台功能不全"，因为**被评测对象的主流形态已经是团队**。
2. **但协作的工程价值不在"角色多"，而在"权限收口"。** 最值得抄的不是 TradingAgents 的 12 个角色，而是 TraderHarness 的一条不变量：**顾问只读、唯一执行者持有下单工具**（★traderharness/agents/committee.py）。这刚好和我们"外部 Agent 只有观察权和提议权"的安全边界同构。
3. **Agent 特定提示词的真正难点是"每个角色能看到什么"，不是"每个角色说什么"。** 所有成熟实现都在 prompt 里显式注入**证据清单**（报告原文、证据编号、verified snapshot），并用"你只能基于以上内容"这类反幻觉条款收口（★TradingAgents market_analyst.py、TraderHarness Advisor.build_prompt）。
4. **主席/裁决角色的输出必须结构化。** TradingAgents 把 Research Manager / Trader / Portfolio Manager 改成 with_structured_output，把"评级"收敛成五档枚举（Buy/Overweight/Hold/Underweight/Sell），并有 REVIEW 兜底 —— 无法解析不等于 Hold（★agents/rating.py）。
5. **记忆是协作的一部分，且必须防穿越。** TradingAgents 的决策日志是 append-only markdown，Phase A 记决策、Phase B 用已实现收益回填反思，读回时用 as_of 过滤掉"当时还不知道的结果"（★decision_log.py）。这是"多轮记忆"和"抗污染"的交点，我们迟早要做。
6. **"有没有账户/撮合"仍然是分水岭。** TradingAgents 自己在 backtest.py 里写死了边界：「This evaluates decision quality. It is not a portfolio simulator, and must not grow one.」（★）而 README 又说 Portfolio Manager 会把单子送进 simulated exchange —— **宣传与实现的裂缝正好是 openOutcry 的立足点**。
7. **学术侧已经出现"常驻评测场"这一层。** Agent Market Arena（AMA，arXiv 2510.11695）用四个 agent 架构（单 agent / 两种风险风格 / 带记忆）在实盘级数据上终身评测。它的存在说明我们 L3 的定位不是空想，但**它不做 A 股、不做人工审批、不做时点掩码**。
8. **建议：短期不做"角色市场"，做"一个 Agent 内部可声明 roles"**。平台协议保持"一次 run 一个 executor 一个账户"，委员会是 Agent Worker 的内部结构（与 TraderHarness 同构），这样既拿到协作能力，又不破坏现有的账户隔离、审批流与回放语义。

## 2. 五种多智能体协作范式（代码级）

### 范式 A：流水线 + 定轮辩论（TradingAgents，118k★）★

**拓扑**（★tradingagents/graph/setup.py、agents/__init__.py）：

~~~text
        ┌──── 分析师组（可开关，各自带专属工具集）────┐
        │ Market / Sentiment / News / Fundamentals   │
        └───────────────────┬───────────────────────┘
                            ▼
        ┌──── 研究员辩论（Bull ⇄ Bear，定轮）────────┐
        │   conditional_logic: count >= 2*rounds     │
        └───────────────────┬───────────────────────┘
                            ▼
                 Research Manager（深思考模型，给投资计划）
                            ▼
                          Trader（提出交易提案）
                            ▼
        ┌──── 风险辩论（Aggressive → Conservative → Neutral）┐
        │   count >= 3*rounds 时收口                        │
        └───────────────────┬───────────────────────────────┘
                            ▼
                  Portfolio Manager（结构化输出五档评级）
~~~

关键工程点：

- **12 个 agent**，全部由工厂函数 create_xxx(llm) 生成，快/深两档模型分流：分析师与辩论者用 quick，Research Manager 与 Portfolio Manager 用 deep（★setup.py）。
- **辩论轮数是配置项而非死循环**：max_debate_rounds / max_risk_discuss_rounds，由 ConditionalLogic 用发言者标签（startswith("Bull")）决定下一个节点（★conditional_logic.py）。代价是**标签即协议**：提示词里改个称呼就会让路由错乱，为此他们把 DEBATE_PATH_MAP 全量映射来兜底（★setup.py 注释里明确写了这是 #1088 的修复）。
- **graph 状态是显式 TypedDict**：InvestDebateState 存 bull_history / bear_history / history / current_response / count；RiskDebateState 存三方 history + latest_speaker（★state.py）。**没有共享聊天室**，只有结构化字段——这是可回放的前提。
- **每个分析师有专属工具白名单**：TOOLS = (get_stock_data, get_indicators, get_verified_market_snapshot)，ToolNode 由同一元组构建（★market_analyst.py）。

### 范式 B：只读顾问委员会 + 唯一执行者（TraderHarness）★

这是**和 openOutcry 最同构、也最该抄**的一种。它把"多智能体"整体降级成一个 Agent 的内部实现：

~~~text
BacktestEngine（共享不可变市场快照）
  └─ CommitteeAgent（一个 Portfolio + 一个 TradingBus）
       ├─ 基本面顾问 ─┐
       ├─ 技术面顾问 ─┼─> CommitteeMemo（每 (day, phase, sub_window) 一份）
       ├─ 新闻顾问   ─┤
       ├─ 多头研究员 ─┤
       └─ 空头研究员 ─┘
       └─ trader/执行者 -> 现有 AgentLoop -> TradingBus.place_order()
~~~

不变量（★docs/design/multi-role-agent.md + AGENTS.md）：

1. 顾问只收到**已掩码**的 Agent 可见消息；
2. 顾问**没有下单工具**（build_prompt 里直接写死"你只能给出分析建议，不能调用工具、不能下单"）；
3. TradingBus.place_order() 是唯一撮合路径；
4. 角色、阶段、**提示词、响应、模型、顺序**全部进轨迹，可确定性重放；
5. 所有顾问与执行者共享同一个 EntityMasker / date_masker；
6. 顾问失败**显式可见**，不做静默兜底。

实现细节（★traderharness/agents/committee.py）：

- @dataclass(frozen=True) Advisor: role, llm_client, instructions，build_prompt 是**纯函数**（"Exposed (not private) so recorded and replayed calls can be verified against the exact same prompt"）——可回放性从提示词构造就开始了。
- 并发：asyncio.gather(..., return_exceptions=True)；失败角色写成 ERROR XxxError: ... 塞回 memo，**不吞**。
- memo 注入：loop.py 在 _run_phase 开头构造 memo → 再对 memo 文本做 date_masker.mask_text 与 entity_masker.sanitize_agent_text → 以 system 消息插入（★loop.py:723-757）。**对顾问输出再做一次遮罩**这一步非常关键：顾问可能把日期/公司名写进正文，绕过工具层遮罩。
- 每个 advisor 的 LLM 调用有独立 scope（advisor_scope_id(agent_id, role)），回放时可单独校验。
- 成本设计：顾问不持有工具，一轮 memo = N 次纯文本调用，比"给每个角色一堆工具"便宜得多。

**为什么这套适合我们**：它不改变环境的账户/撮合/审批语义，只是让"一个 Agent"变成"一个委员会"。平台协议（observation/action）完全不用动。

### 范式 C：角色扮演基金 + 单管线三模式（ai-hedge-fund v2，64k★）★

它的多智能体**不是辩论**，而是"组织架构"：

~~~text
FUND = Allocator(CIO) over STRATEGIES
STRATEGY = PortfolioPolicy over ANALYSTS
ANALYST = AlphaModel -> Signal(conviction ∈ [-1,1] + thesis)
~~~

- 分析师有两种同接口实现：**LLM 投资人 persona**（Buffett / Munger / Lynch / Druckenmiller…）与**纯数学量化模型**（PEAD、动量、regime），后者不带 LLM 调用。★hedge_fund/signals/ 下 buffett.py 与 pead.py 并列。
- LLMAgent 的契约非常值得抄（★signals/llm_agent.py）：
  - persona 就是 get_system_prompt() 一个方法；user prompt 默认是**点时可用的基本面快照** snapshot.render()；
  - 输出 JSON {signal: bullish/neutral/bearish, confidence, reasoning}；
  - **失败契约**：数据层错误必须抛（fail loud），LLM/解析失败则 **abstain**（value=0，标记 abstained）——绝不把"调用失败"伪装成"中性观点"；
  - **prompt cache 以 (agent, model, system, user, snapshot_hash) 为 key**，同一快照不重复付费；
  - 文档里一句话点题："What this persona is allowed to know"（build_snapshot 可被子类覆盖）——**角色能力=可见数据范围**，这正是我们"研究工具白名单"要的语义。
- 三层可插拔（allocator / strategy / analyst）+ 一条 run_cycle 管线，回溯/纸面/实盘只换时钟和 broker（★VISION.md）。这条"一个 code path"原则，和 openOutcry"SFT 与评测同源"的诉求一致。

### 范式 D：角色按市场制度扩展（A 股衍生层）★

- **TradingAgents-CN（32.7k★）**：已从"投研脚本"长成平台。分析师扩到 **7 个**（market / fundamentals / news / social_media / **china_market** / sector / **index**），加 research_manager + risk_manager + bull/bear + 三风险辩论者 + trader，约 15 个角色（★tradingagents/agents/ 目录）；配套 ChromaDB + embedding 的 memory.py（46kb）、FastAPI + MongoDB/Redis 的 app/（含 paper 模拟盘、skills、workflows、scheduler）（★目录结构）。
- **它最值得抄的一条：把"角色输出契约"做成独立模块**。compliance_prompting.py 给每个角色定义**允许的输出段落**与**禁止项**（"market_analyst 输出结构限定为：技术特征、趋势观察、波动与量价特征、风险提示、后续观察信号"；全局禁止输出目标价、止损价、仓位比例、胜率等执行性内容）（★utils/compliance_prompting.py）。这就是"agent 特定提示词"的产品化形态：**不是一段自由文本，而是一份角色规格**。
- **TradingAgents-astock（3.8k★）**：分析师从 4 → 7，新增**政策分析师 / 游资追踪 / 解禁监控**；输出中文、内部辩论仍用英文以保证推理质量；Alpha 基准换成沪深 300（☆README）。
- 它还解决了两个我们一定会遇到的问题：**分角色模型**（role_llms 表 + ROLE_KEYS + GraphSetup.llm_for(role)）与**决策绩效统计**（direction_accuracy 口径：看多要跑赢、看空要跑输才算对，Hold 不计入）（☆CLAUDE.md，v0.5.0/v0.5.2）。
- **KylinMountain/TradingAgents-AShare（882★）**：15 Agent 机构式协作 + 全流程可视化，宣称可接 OpenClaw / Claude Code（☆仓库描述）。
- 结论：**"角色数量"是可快速复制的表层，"角色对应的数据接口与制度约束"才是护城河**。我们要复制的话，应该按 A 股制度切角色（公告/龙虎榜/解禁/政策/资金流），而不是照抄美股四分析师。

### 范式 E：多账户同场竞技（竞技场路线）☆

TraderHarness 的 compare、Hyper-Alpha-Arena、AMA、以及我们自己的"运行对比"都属于这一类：**同一种子、同一遮罩、同一起始资金，各自独立账户，最后排名**。要点不是"谁 AI 更聪明"，而是**可比性**：同数据版本、同规则版本、同费用模型、同基准。TraderHarness 为此把"独立多 Agent compare 在每个交易日内串行执行"写成不变量（★AGENTS.md 第 9 条：并发曾导致共享内存帧竞态、破坏指纹回放）。

> 这一范式与"协作"是**互补而非替代**：协作产生一个账户，竞技比较多于一个账户。openOutcry 若两者都做，必须明确"委员会 = 一个参赛单元"，否则账户归属和排名口径会打架（TraderHarness 明确把"多执行者共享账户"列为**有意排除**项）。

## 3. Agent 特定提示词：四种组织方式与一个通用骨架

### 3.1 四种落法（按可维护性排序）

| 方式 | 代表 | 长相 | 优缺点 |
|---|---|---|---|
| ① 硬编码 f-string | TradingAgents | prompt = f"""You are a Bull Analyst...{reports}...""" | 零依赖、改起来快；但 12 份 prompt 散在 12 个文件，无法版本化对比 |
| ② 角色 + 指令两段式 | TraderHarness | f"你是交易委员会中的{role}顾问。{instructions}\n你只能给出分析建议..." | **强制能力边界写在框架层**，角色只填 instructions；最省 token，最适合"用户自定义角色" |
| ③ persona = 一个方法 | ai-hedge-fund | get_system_prompt() 返回人格；user prompt = 结构化快照 | 契约清晰（signal/confidence/reasoning），便于缓存与 abstain |
| ④ 外置配置/模板 | TraderHarness advisors: YAML、PanWatch prompts/*.txt（chart_analyst / premarket_outlook / intraday_monitor / news_digest / daily_report） | 一个角色一个文本文件 | 用户可加角色、可 A/B；需要 schema 校验与版本号 |
| ⑤ 角色输出契约（合规层） | TradingAgents-CN | 每角色一段"允许的输出段落 + 禁止项"，与角色 prompt 分离 | **最适合评测平台**：可机器校验"角色越界"（如顾问输出了目标价），直接变成扣分项 |

**给 openOutcry 的直接建议**：Agent 规格卡里加 roles: [{id, name, model, prompt, tools, budget}] + executor_role，落在**外置配置**（方式④），但**能力边界由平台注入**（方式②）——角色 prompt 只写"怎么看"，不写"能干什么"。

### 3.2 每个角色 prompt 的通用骨架（从四家实现里提炼）

~~~text
[身份]      你是 <角色>，在 <团队> 中负责 <职责>。            ← 唯一随角色变化的部分
[可见证据]  只可使用以下已遮罩材料：<报告原文/证据编号/快照>   ← 由平台注入，角色不可自取
[输出契约]  评级必须是 Buy|Overweight|Hold|Underweight|Sell / 或 JSON schema
[能力边界]  你不能调用工具、不能下单、不能联网                    ← 框架层写死，非角色可改
[反幻觉]    若与 verified snapshot 冲突，请指出冲突而不是自行调和
[语言/风格] 中文输出；以对话方式辩论而非罗列数据
~~~

真实片段对照：

- **边界写进框架**（TraderHarness，★committee.py:30-33）：
  > 你是交易委员会中的{role}顾问。{instructions}\n你只能给出分析建议，不能调用工具、不能下单。
- **反幻觉写进角色**（TradingAgents，★market_analyst.py:47）：
  > Before writing the final report, call get_verified_market_snapshot ... treat it as the source of truth ... If another tool's output conflicts with the verified snapshot, flag the discrepancy rather than inventing a reconciled number.
- **输出契约写进主席**（TradingAgents，★portfolio_manager.py）：五档评级 + Executive Summary + Investment Thesis，并显式要求"辩论必然有冲突，决定哪边更强是你的工作，冲突本身不是 Hold 的理由"。
- **空位不清空**（TradingAgents，★context.py:opponent_argument_or_opening）：对手还没发言时，注入"(The bear analyst has not spoken yet — open the debate with your own case.)"，否则模型会**编造对手立场**。这条对我们同样致命：任何"让 Agent 回应上一条"的设计都要处理空位。

### 3.3 三个已知坑（都是别人踩过的）

1. **标签即路由**：TradingAgents 用 current_response.startswith("Bull") 决定下一节点，改称呼=改拓扑（#1088 全量 path_map 兜底）。→ 我们用显式 speaker_id 字段，别靠文本前缀。
2. **共享上下文串味**：分析师之间用 RemoveMessage 清场（create_msg_delete），否则后一个分析师会接着前一个的话题写。→ 我们的新"角色"若共享事件台账，必须按角色切视图。
3. **结构化输出与工具互斥**：TradingAgents 发现 schema-only structured output 只绑定一个工具，模型若试图调搜索工具就整次作废，于是显式加 NO_EXTERNAL_TOOLS 约束（★structured.py）。→ 主席/裁决角色一律禁工具，顾问角色按需给只读工具。

## 4. 记忆与反思：协作跨轮的前提

TradingAgents 的 TradingMemoryLog（★decision_log.py）是目前最干净的实现，值得整体借鉴：

- **append-only markdown**，条目分隔符用 HTML 注释 <!-- ENTRY_END -->（"cannot appear in LLM prose output"）；
- **Phase A**（决策时）：写 [date | ticker | rating | pending] + DECISION 原文，**零额外 LLM 调用**；同 (date,ticker) 幂等去重；
- **Phase B**（持有期结束后）：换算出 raw/alpha 收益，调一次 reflection 生成 2-4 句散文，回填 REFLECTION 段；
- **读回时按 as_of 过滤**：只保留 resolved <= as_of 的条目 —— "不让回测从尚未发生的结果里学习"（#1251）。这条把"记忆"和"防穿越"打通了；
- 注入粒度：同标的最近 5 条全文 + 跨标的最近 3 条仅反思，避免上下文膨胀。

TraderHarness 走另一条：**每天上下文 reset，跨天靠记忆摘要追加**，并把 system prompt 的**不变前缀**（角色/规则/工具说明/股票列表）放在缓存边界之前，记忆追加在边界之后，只在超限时压缩（★CLAUDE.md）。这两条路对我们的意义不同：

- 若 openOutcry 要做**跨日训练轨迹**（L3 的训练价值所在），应选 TradingAgents 的"可审计日志 + 事后反思"，因为它是**可回放、可过滤、可打分**的；
- 若要做**长跑模拟盘**，TraderHarness 的缓存友好分层能显著省钱。

## 5. 学术侧：协作到底值不值

| 工作 | 机制 | 对我们的用法 |
|---|---|---|
| TradingAgents（arXiv 2412.20138，q-fin.TR，Oral @ Multi-Agent AI in the Real World） | 模拟交易公司的角色分工 + Bull/Bear 辩论 + 风险团队；宣称在累计收益、Sharpe、最大回撤上优于基线 | 引用作"协作有效"的基线；注意其评测是**决策级**，无组合 |
| Agent Market Arena（arXiv 2510.11695，"When Agents Trade"） | **终身/实时**多市场评测：InvestorAgent（单 agent 基线）、TradeAgent、HedgeFundAgent（不同风险风格）、DeepFundAgent（带记忆） | 证明"常驻评测场"是学术认可的 L3；其结论"**agent 架构差异 > 模型主干差异**"正好是我们"测 Agent 不测模型"的论据 |
| MultiAgentBench（ACL 2025） | 同时评协作与竞争的 multi-agent 基准 | 可参考其协作指标（里程碑达成、通信开销） |
| Debate or Vote（NeurIPS 2025） | 辩论 vs 投票哪种更好 | 提示我们：辩论不是万能，需按任务选聚合方式 |

**一条可写进 FYP 报告的判断**：AMA 已经证明"骨架比模型重要"，但它的四个 agent 都是**单 agent 变体**，没有真正的委员会；TradingAgents 有委员会但**没有账户**。**"委员会 × 真实账户 × 时点掩码"这个组合，目前无人公开交付。**

## 6. 对 openOutcry 的落点（三条路线，建议选 B）

### 路线 A：不做（保持单 Agent 评测台）

- 优点：范围小，答辩风险低。
- 缺点：评审会问"你评测的对象是 2026 年的主流形态吗"，而主流已是团队；且我们在 4.1 竞品对比里已经写了"多智能体横向竞技"，如果不做协作，这个词只能理解成"多个单 Agent 比赛"。

### 路线 B：委员会作为 **Agent 内部结构**（推荐）

平台协议不变，一个 run 仍对应一个 Agent 会话、一个账户、一个执行者：

~~~text
Agent 规格卡
├─ executor: {model, prompt, tools, budget}        ← 唯一下单者，走现有人机审批
└─ roles: [ {id, name, model, prompt, tools:readonly} ... ]
      ↓ 每个交易日按阶段（盘前/开盘/尾盘）并发调用
   CommitteeMemo（带证据编号）→ 注入 executor 上下文（再做一次时点遮罩）
~~~

收益：

- 零改动撮合/账户/审批/回放语义（TraderHarness 已验证可行）；
- 评测维度可以新增**协作增益**：同一 executor 单跑 vs 带委员会跑（消融），这正好呼应我们已有的"工具消融"叙事；
- 事件台账天然能记 advisor.called / memo.injected / dissented，证据链更厚；
- 对外部 Agent：委员会是它自己的事，平台只要求"一个 executor"，协议不用改。

成本：

- 每个阶段 N 次额外 LLM 调用（可控：顾问无工具、无多轮）；
- 需要 roles 的版本化（与现有"不可变快照 Hash"合并）。

### 路线 C：委员会作为**一等公民**（角色级事件、角色级排名）

- 优点：可视化和学术叙事最强（"我们能测分工是否有效"）。
- 缺点：账户归属、审批归属、排名口径全部要重定义；TraderHarness 明确把"多执行者共享账户"列为有意排除项——他们踩过这个坑。

### 6.4 建议的下一步（不改现有 MVP 范围，先补 3 个可交付物）

1. **协议层**：Agent 规格卡加 roles + executor_role（设计文档即可，不写代码）；
2. **事件层**：事件枚举加 advisor.requested / advisor.responded / memo.injected / executor.decided（4 个事件，复用现有台账）；
3. **评测层**：指标表加一列"协作增益 = 带委员会 − 单 executor"，作为消融实验的一种，与"工具消融"并列。

这三条都不需要动撮合引擎，却能把"多智能体"从**竞品有而我们没有**变成**我们有而竞品没法公平度量**。

### 6.5 一个只有我们能做的增量：**角色边界审计**

TradingAgents-CN 把"角色不许说目标价/仓位"写进了 compliance_prompting.py，但它**无法证明**角色真的没越界——只能靠人工看报告。而 openOutcry 有**事件台账 + 证据编号**，可以把这件事变成**自动指标**：

| 可审计项 | 判定方式 | 数据来源 |
|---|---|---|
| 顾问越权（给了目标价/仓位） | 角色输出正则/规则命中 | advisor.responded 事件正文 |
| 顾问幻觉（引用了不存在的证据） | 抽取 [ev_xxx] 与证据表求差集 | 证据编号 + 证据快照 |
| 执行者采纳率 | 采纳的建议数 / 注入的建议数 | memo.injected + order.proposed |
| 协作增益 | 同一 executor 单跑 vs 带委员会 | 两次 run 的指标差 |
| 协作成本 | 额外 token / 延迟 / 工具调用 | token 预算账本 |

这套"**协作可被审计**"的指标，目前**没有任何一个开源项目提供**（TradingAgents 只给最终评级，TraderHarness 只把 memo 写进轨迹但不打分，CN 只做提示词约束）。它比"我也有多智能体"更适合写进 FYP 的贡献点。
