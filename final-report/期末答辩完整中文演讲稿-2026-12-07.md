### Slide 01｜答辩开场封面：项目立意与定位破题（`cover-evaluation-ground`）

各位老师好！今天向大家汇报并推介我们的毕业设计项目——**openOutcry**。
它是一个**面向任意投资 Agent 的评测与训练场**：让投资者在历史股市的真实模拟中，亲眼见证 Agent 的交易决策，并与它一起进步。在展开系统细节之前，我想先带大家看一眼今天金融 AI 领域正在发生的真实变化。

### Slide 02｜商业产品浪潮：金融 Agent 正在崛起（`commercial-wave`）

过去一年，AI 在金融领域已经跨过了“陪聊写摘要”的初级阶段，真正演变成触手可及的商业化 Agent。
在海外，OpenAI 推出了面向金融机构的专属智能体套件；在国内，Kimi K3.1 Pro 把深度研究直接打进财报与估值建模；而更贴近普通股民的同花顺问财，甚至直接上线了 SkillHub 技能广场——普通散户复制一句指令，就能给自己的本地 Agent 装上全套选股与财务分析技能。

### Slide 03｜开源与大众热度：散户与开发者的注意力已被彻底点燃（`attention-first`）

与商业终端同步爆发的，是开源社区和普通投资者的极高热情。
GitHub 上主打多角色协作的 `TradingAgents` 已经斩获超过 11 万颗 Star；在海外，YouTube 散户实测 AI 炒股的视频频频破数十万播放，华尔街财经媒体也连续专题拆解 AI 交易员的真实表现；回到国内 B 站，大家动手测 AI 炒股同样热度极高。越来越多投资者，已经不再满足于只围观别人的静态演示，而是想亲自尝试。

### Slide 04｜热潮之下，投资者心中的顾虑是什么？（`two-questions`）

但热潮之下，真要掏出真金白银的时候，投资者心里其实都有同一个顾虑。
今天很多人用 AI 炒股，本质上是在做 **vibe trading**——看 AI 写出一份头头是道的分析，就凭感觉跟着下单。
可 AI 真的像演示里那样无所不能吗？看看持续运行最久的公开实盘基准 **TradeRank**：11 个完整赛季、78 个模型、3,100 多笔交易下来，只有 **38.9%** 的模型-赛季最终盈利，冠军几乎每季换人；牛市顺风时也许还不错，8 月和 10 月榜首能跑到 12% 左右，可一旦行情转熊，AI 照样大面积亏损——第 3 赛季连冠军都是负 0.63%，11 月大盘回调时，22 个前沿模型里只有 1 个赚钱。
所以投资者真正卡住的，从来不是指望 AI 当一个稳赚不赔的股神，而是**不敢直接拿真金白银，去赌一个没上过场的 AI**。
这就是我们打造 **openOutcry** 的出发点：做一个**面向所有散户的 AI 训练场**——在真金白银进场之前，把你自己的投资 Agent 放进我们的模拟盘里，先看真实结果，再决定要不要信它。

### Slide 07｜切身调研：两类真实散户，两种卡点（`one-good-call`）

为了搞清楚这个问题，我没有凭空假设。作为一名计算机学生，我自己也是一名 A 股散户。围绕“为什么不敢把真金白银交给 AI”，我访谈了身边最典型的两类人。

**第一类，是我父母那辈的老股民。**
他们有多年实盘经验，其实并不排斥新技术——平时会用 AI 查资料、看财经新闻，也会点开支付宝、同花顺这些软件里集成的 AI 服务问股票。但聊到“敢不敢真按它说的买”，他们卡在同一个问题上：**看不到这些 AI 的真实历史成绩。** 每次问它都头头是道，可把它放进过去一轮牛熊里连续跑，到底赚过还是亏过、大跌时回撤多少，完全是一笔糊涂账。他们自己也没能力搭考场去验，所以只能把 AI 当新闻助手看，绝不敢托付真钱。

**第二类，是包括我在内、身边懂技术也在炒股的同学。**
我们有折腾 Agent 的经验，会自己搭开源框架、改提示词、换大模型、接各种财经 Skill。但我们遇到的难题恰恰相反——**改完配置之后，就像在“蒙眼拧螺丝”。** 今天加一条止损规则、明天换个新模型，放到市场上跑两天赚了钱，我们根本分不清：**到底是这次改动让 Agent 变强了，还是纯粹撞了大运、碰上大盘涨了？**

两类人背景截然不同，但归根结底都在问同一件事：市面上现有的服务，为什么解决不了他们的验证难题？

### Slide 08｜现有服务对比：为什么现有产品都解不了？（`tools-but-no-chain`）

回到市场上，散户最容易想到的其实是两类现成服务，但它们各自都有明确边界：

- **第一类，现有投资 AI 与 Agent 服务**，比如支付宝、同花顺里的 AI 服务或各类投研助手：它们擅长整理资讯与分析观点，但**不接入连续交易**，而且受限于**合规要求，只能局限于给出简单的投资建议**；老股民照样看不到它们在真实市场规则下的历史成绩。
- **第二类，现有模拟盘 / 模拟炒股服务**，比如主流券商或行情软件的模拟盘：它们本质上是**面向真人手动练手设计的，无法直接接入外部 Agent**，也缺乏面向 Agent 的决策轨迹记录与同条件复测能力。

放眼整个市场，**当下并没有一个真正跑出来的 killer 级应用，能够帮助散户和个人开发者完成投资 Agent 的训练、优化与模拟实战演练。**

### Slide 09｜核心需求：从痛点与空白，长出三项硬要求（`four-requirements`）

遵守真实交易规则的模拟环境只是基础，现有的模拟盘其实都能做到。把这两类人的痛点和现有服务的缺口收束起来，目前市面上真正尚未被满足的，其实是这**三项核心需求**：

- **第一，容易接入。** 无论是只想挑个现成模板验成绩的老股民，还是想接进自己外部 Agent 的开发者，都能以可接受的成本直接上场。
- **第二，过程可理解。** 不只给一条收益曲线，而是把每笔交易背后**看到了什么、引用了哪条证据、为何下单、账户怎么变**串成完整轨迹，赢要明白，亏更要找得到病根。
- **第三，可重复对照。** 锁死同一段历史区间、初始资金和市场规则，改完提示词、模型或 Skill 后能在**同等条件下重跑对比**，把“策略变强”和“行情运气”彻底分开。

### Slide 10｜定位收束：不是再造一个荐股 AI（`not-another-stock-picker`）

所以，openOutcry 真正要做的，**不是再造一个告诉大家买什么股票的荐股 AI**。

而是补上市场上缺失的那块拼图——给每一位散户建一座**先试炼、再信任的 AI 训练场**，让你有能力亲眼看清：**自己的 Agent 到底表现如何、为什么会这样、以及下一步该怎么改。**

### Slide 11｜小结与交棒：交给产品方案与现场原型（`handoff-to-part-3`）

小结一下：这三项需求不是一份功能清单，而是我们设计整套系统的三条硬约束。

## 04 · 系统架构、实现细节与诚实评估（Slide 13–18｜约 7 分 15 秒）

### Slide 13｜系统架构与职责边界：Agent 做决策，平台管事实（`agent-decides-platform-owns-facts`｜约 1 分 15 秒）

在拟定的目标系统架构中，我们将 **Agent 推理层**与**市场模拟引擎**彻底分离（如果需要查看通信契约细节，原型侧边栏底部的「参考 → 协议与 Skill」里也整理了完整的 `Observation / Action / Event` JSON 定义）。

**Agent 适配器**负责连接不同的 Agent 运行环境：控制面计划收敛为 **ACP（Agent Client Protocol）**，工具面通过 **MCP** 按环境切换受控工具——历史场注入 PIT 截断证据工具，实战场注入实时行情工具。

但有两条架构铁律不会妥协：第一，模拟时钟、规则校验、撮合结果和账户余额的**最终权威必须掌握在平台手里，而不是语言模型手里**——Agent 说一句“我买入了 100 股”，绝不等于一笔合法订单已经成交。

第二，在**时间粒度**上，我们采用**「快慢双时钟解耦」**架构：A 股虽然日内振幅可能很大，但让大模型逐秒或逐分钟推理既烧钱又会诱发高频噪音过度交易；因此**慢时钟（LLM Agent）**只在固定关键窗口（盘前/开盘/尾盘）或异动事件触发时唤醒做低频语义决策，而**快时钟（确定性代码引擎）**负责按规则扫描行情、执行限价/止损条件单与风控——MVP 首版先落地最干净、最可复现的日频三阶段，二期再演进到 5 分钟级渐进撮合与盘中条件单。

需要说明的是，这里介绍的是**目标后端架构**，并不是说完整协议接入和交易引擎已经部署完成。

### Slide 14｜三项关键设计取舍：评估可信，取决于三道边界（`three-boundaries-of-trust`｜约 1 分 30 秒）

其中有三项设计尤其重要。

**第一，双重抗污染：时点截断（PIT）+ 实体日期遮罩。** 在历史实验中，不仅要按模拟时钟严格过滤公告与行情（防止未来信息泄漏），还要考虑通用大模型可能从训练语料中背诵过明星股与历史大涨日；因此研究网关既做 `as_of` 时点截断，又支持把标的与日期匿名化为 `公司-017`、`D+0`，把“前视偏差”和“模型记忆污染”分开治理。

**第二，真实市场交易规则（当前优先接入 A 股）。** 模拟引擎按所接入市场的真实制度执行——以中国 A 股为例，系统必须强制校验 T+1 卖出限制、停牌、±10%/±20% 涨跌停、100 股整手、可用资金和交易费用。提出交易意向和市场真正成交，永远是两个独立事件。

**第三，人工介入留痕与可复现性。** 无论历史场改单审批还是实战场采纳/修改，系统都必须保留原始建议与最终操作的双轨记录；修改配置重跑时锁死数据区间、资金与规则；同时严格区分“不重调模型的确定性轨迹回放”与“重新推理的新运行”。

这些设计不是装饰性的功能，它们是在保护评估结果本身的意义。

这套设计有相当大的目标。因此，对第一学期的期末汇报来说，最重要的问题是：**目前究竟有哪些部分已经运行起来，哪些仍然是工程目标？** 接下来我会清楚地区分两者。

### Slide 15｜第一学期实现范围：Term 1 交付了什么？（`term1-what-shipped`｜约 55 秒）

第一学期，我最主要的交付成果，就是刚刚向大家现场演示的**可运行、可交互的 openOutcry 网页原型**。它使用 React、TypeScript、Vite 和 React Router 构建。在接入可用于实际实验的模拟后端之前，我首先着重解决如何把完整的五步用户决策流程做得清晰、可理解、可交互。

代码中已经包含 Agent 库与配置卡、训练委托单、历史训练场、账户与持仓台账、复盘对照视图、实战镜像工作台以及决策证据弹窗。我没有把每个页面当成独立的静态效果图，而是通过一个中心状态机，让用户操作能够一致地改变当前运行状态及相关界面。

这里有一个必须强调的边界：当前原型使用的是**虚构示例公司、预设事件和模拟组合数值**。界面上展示的收益仅用于演示，**不是经过测量的真实股市投资表现，不是经过验证的历史回测结果，也不是外部真实 Agent 的运行成绩**。

### Slide 16｜工程细节：一笔订单，是四个不同事件（`one-order-four-events`｜约 1 分 05 秒）

我想重点介绍一个刚才在训练场里大家已经亲眼看到的实现选择：一笔订单如何在不同状态之间推进。

一笔**订单提案**，首先只是交易意图。当用户批准或修改它时，订单才进入已提交状态；仅仅因为用户批准了订单，账户就立刻发生变化，这是不合理的。必须经过独立的模拟撮合动作并推进时钟之后，持仓和现金才会更新，同时系统追加一条成交事件记录。相反，如果用户拒绝订单，账户就应保持不变。

在当前原型中，这些状态变化通过基于 reducer 的运行状态机实现。事件流、截断走势解锁、持仓和组合统计都基于同一份底层状态，而不是由不同页面分别维护可能相互矛盾的数据副本。

这是一个有意义的**交互与领域模型原型**。不过，当前演示撮合中的成交价格和费用仍然写死在前端代码里。未来还需要使用真实历史数据，并由经过测试的执行引擎替换这些演示逻辑。

### Slide 17｜证据边界：我们已验证交互，尚未验证收益（`verified-vs-unverified`｜约 1 分钟）

刚才的五步演示可以说明原型具备三项有价值的特征。

第一，从 Agent 接入、委托定口径、训练场人机审批撮合，到对照复盘与实战镜像辅助，整条端到端决策流程能够被组织成清晰、可审计的交互闭环，而不只是一段聊天回答。第二，人工批准、修改和拒绝可以被明确留痕，且与市场成交严格解耦。第三，界面可以把订单状态、投资组合变化和事件历史绑定在同一个状态源上。

但这**并不能证明**外部 Agent 已经能够自主完成交易决策，也不能证明首个接入的 A 股交易规则引擎已经完整运行，或者历史信息的时点约束已经得到验证。这些仍然需要后端接入和专门测试。

在学术答辩里，这个区别很重要：一个逻辑完整的交互界面，确实是项目进展；但它还不等于一个已经通过实验验证的评测平台。

### Slide 18｜验证计划与尚存差距：下一步，怎么证明它可信？（`how-to-prove-it-next`｜约 1 分 30 秒）

在软件工程层面，仓库已经配置了 TypeScript 检查、生产构建、单元测试和 UI 审查脚本，也包含对工具计算与派生状态的测试。这些为检查代码质量和交互一致性提供了方法。不过，如果没有最新一次测试的实际运行记录和输出，我不会宣称某个具体的通过数量或性能指标。

在下一阶段的评估中，我计划分四层开展验证。

**第一层，界面与状态转换。** 检查批准、修改、拒绝、模拟成交、委托创建、错误状态和账户约束。例如，一笔被拒绝的订单不应该改变可用资金。

**第二层，市场规则正确性。** 使用固定的历史数据集，对 T+1 约束、停牌、涨跌停、交易费用、持仓变化和投资组合计算进行测试，并与已知正确结果核对。

**第三层，时间信息完整性。** 人为放入一份发布时间晚于模拟日期的公告，检查 Agent 是否确实无法检索到它。这可以证明时点过滤是否真正生效，而不只是写在架构图里。

**第四层，受控对照实验。** 在相同数据和规则条件下多次运行，记录配置版本和人工介入情况，并区分确定性的轨迹回放与重新调用模型产生的随机性决策。只有到这一步，收益、回撤和横向比较图才具有可辩护的实验意义。

在当前阶段，后面这些测试仍属于**评估计划**，而不是已经完成的实证结果。这也是第一学期交付成果最主要的局限。

## 05 · 结论与后续工作（Slide 19–20｜约 1 分 30 秒）

### Slide 19｜总结与下期里程碑：让 Agent 先可测试，再谈可信（`testable-before-trustworthy`｜约 1 分 20 秒）

最后，我想用一个问题的转变来总结 openOutcry。我们不再只问：一个 Agent 能否给出有说服力的股票推荐？而是进一步问：用户能否**评估它连续做出的决策、理解这些决策的后果，并在可比较的条件下持续改进它**？

这一学期，我明确了产品需求，调研了 Agent 接入协议、市场模拟与时间粒度取舍中的关键问题，设计了目标系统架构，并实现了一个交互式前端原型，用来展示五步闭环用户流程，以及订单提案、人工批准和模拟执行之间的区别。

这已经为未来的 Agent 评估环境打下基础，**但还不是一个已经完成的评估平台**。

下一阶段，我会优先通过选定协议接入 Agent，建立历史行情数据与交易模拟后端（优先完成中国 A 股接入），实现符合模拟时点的信息访问控制，持久化保存完整事件轨迹，并在此基础上开展可复现的实验，计算明确的风险与绩效指标。

下一阶段最重要的里程碑，并不是把界面打磨得更漂亮，而是能够展示**一次完整且可核验的运行**，以及一次受控重跑，并清楚解释两次运行之间的差异。

### Slide 20｜致谢与问答：Thank you. Questions?（`closing-thank-you`｜约 10 秒）

归根结底，openOutcry 想做的，是让投资 Agent **先变得可测试，再谈是否值得信任**。
