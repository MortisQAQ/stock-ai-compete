## 01 · 引言：背景与动机（Slide 01–05）

### Slide 01｜答辩开场封面：项目立意与定位破题（`cover-evaluation-ground`）

各位老师好！今天向大家汇报并推介我们的毕业设计项目——**openOutcry**。
它是一个**面向任意投资 Agent 的评测与训练场**：让投资者在历史股市的真实模拟中，亲眼见证 Agent 的交易决策，并与它一起进步。在展开系统细节之前，我想先带大家看一眼今天金融 AI 领域正在发生的真实变化。

### Slide 02｜商业产品浪潮：金融 Agent 正在崛起（`commercial-wave`）

过去一年，AI 在金融领域已经跨过了“陪聊写摘要”的初级阶段，真正演变成触手可及的商业化 Agent。
在海外，OpenAI 推出了面向金融机构的专属智能体套件；在国内，Kimi K3.1 Pro 把深度研究直接打进财报与估值建模；而更贴近普通股民的同花顺问财，甚至直接上线了 SkillHub 技能广场——普通散户复制一句指令，就能给自己的本地 Agent 装上全套选股与财务分析技能。

### Slide 03｜开源与大众热度：散户与开发者的注意力已被彻底点燃（`attention-first`）

与商业终端同步爆发的，是开源社区和普通投资者的极高热情。
GitHub 上主打多角色协作的 `TradingAgents` 已经斩获超过 11 万颗 Star；在海外，YouTube 散户实测 AI 炒股的视频频频破数十万播放，华尔街财经媒体也连续专题拆解 AI 交易员的真实表现；回到国内 B 站，大家动手测 AI 炒股同样热度极高。越来越多投资者，已经不再满足于只围观别人的静态演示，而是想亲自尝试。

### Slide 04｜热潮之下，投资者心中的顾虑是什么？（`two-questions`）

但热潮之下，真要掏出真金白银的时候，投资者心里其实都有同一个顾虑。
今天很多人用 AI 炒股，本质上是在做 **vibe trading**——看 AI 写出一份头头是道的分析，就凭感觉跟着下单。
可 AI 真的像演示里那样无所不能吗？看看持续运行最久的公开实盘基准 **TradeRank**：11 个完整赛季、78 个模型、3,100 多笔交易下来，只有 **38.9%** 的模型-赛季最终盈利，冠军几乎每季换人；牛市顺风时也许还不错，8 月和 10 月榜首能跑到 12% 左右，可一旦行情转熊，AI 照样大面积亏损——第 3 赛季连冠军都是负 0.63%，11 月大盘回调时，22 个前沿模型里只有 1 个赚钱。
所以投资者真正卡住的，从来不是指望 AI 当一个稳赚不赔的股神，而是**不敢直接拿真金白银，去赌一个没上过场的 AI**。
这就是我们打造 **openOutcry** 的出发点：做一个**面向所有散户的 AI 训练场**——在真金白银进场之前，把你自己的投资 Agent 放进我们的模拟盘里，先看真实结果，再决定要不要信它。

## 02 · 用户痛点与核心需求（Slide 06–12）

### Slide 06｜第二幕章隔页：为什么用户不敢把钱交给 AI？（`act02-cover`）

第二部分，我们聚焦用户痛点与核心需求。
承接上一部分，这一幕核心只回答一个问题：为什么用户不敢把钱交给 AI？
下面我们先从一个具体场景看起。

### Slide 07｜一个场景：一次对，不等于可信（`one-good-call`）

刚才我们看到，在公开榜单上 AI 遇到熊市照样会亏。落到散户自己手里，情况其实更隐蔽——让我们想象这样一位投资者：他已经开始用 AI Agent 分析股票。

有一天，Agent 推荐了一只股票，理由听起来很充分。第二天，这只股票真的上涨了。

这当然令人兴奋。但问题来了：**一次正确的推荐，就足以说明这个 Agent 值得信任吗？**

如果把它放到过去几个月的市场里持续运行，结果会怎样？面对下跌，它能控制多少风险？如果我们修改了提示词，再测一次，表现到底有没有改善？

一份看起来很专业的分析报告，并不能直接回答这些问题。

### Slide 08｜两类人，两个卡点：降门槛与提可信度（`two-kinds-of-users`）

这类困惑并不只属于普通投资者。

对希望尝试 AI 投资的人来说，困难在于：即使会用 AI，也未必具备搭建完整测试环境的能力，更难判断一连串交易结果究竟意味着什么。

对自己开发或改造 Agent 的人来说，问题又不太一样：他们可以接入新工具、调整策略和风控提示词，却需要一种可靠的方法，来比较修改前后的表现。

**一类人需要降低验证门槛，另一类人需要提高验证的可信度。** 他们共同关心的，不是 Agent 能否给出漂亮的答案，而是能否看清它持续做决策时的真实表现。

### Slide 09｜现有工具：工具不缺，过程是断的（`tools-but-no-chain`）

事实上，现有市场上并不缺少优秀工具。

金融 AI 助手擅长整理信息、形成投资观点；专业量化框架能进行历史回测；模拟交易平台能提供实盘节奏；而像第一部分提到的 TradeRank 这类公开评测，虽然能帮我们看清主流大模型的盈亏规律，但跑的是别人的加密和美股榜单，依然测不了你自己手里的 A 股 Agent。

但如果用户想检验的是**自己手里的 Agent**，情况就复杂了：如何让它参与连续的历史决策？如何把 A 股交易约束算进去？如何知道每一步为什么买卖？调整配置后，又怎样在可比条件下复测？

这些能力可能分散在不同工具和流程中，用户往往需要自行拼接。**我们关注的不是“现有工具都做不到”，而是完整验证过程仍不够顺畅。**

### Slide 10｜四项核心需求：把困惑变成四项要求（`four-requirements`）

因此，我们把这段用户旅程归纳为四项核心需求。

**第一，容易接入。** 无论是普通用户还是已有 Agent 的开发者，都应该能以可接受的成本开始测试。

**第二，真实试炼。** 不只评价单次回答，而是在考虑 A 股市场规则的历史模拟中观察连续决策及其风险。

**第三，能够理解。** 用户不仅要看到收益结果，还要能回顾关键交易和决策依据，知道问题可能出在哪里。

**第四，可重复比较。** 修改配置之后，需要尽量保持测试条件一致，避免把市场变化或偶然性误认为改进效果。

### Slide 11｜反向定位：不是再造一个荐股的 AI（`not-another-stock-picker`）

所以，我们真正要解决的，不是再造一个告诉用户买什么股票的 AI，**而是让用户有能力判断：自己的 Agent 究竟表现如何，为什么会这样，以及下一步该怎样改进。**

这三件事，就是第三部分要回答的问题。

### Slide 12｜小结与交棒：交给系统设计（`handoff-to-part-3`）

小结一下：这四项要求不是一份功能清单，而是整套系统的设计约束。
至于技术路径、实际完成度和测试证据，我会分别放在第三和第四部分。
下面进入第三部分：openOutcry 如何围绕这四项目标，设计整个系统。

## 03 · 解决方案与系统设计（Slide 13–16｜约 4 分钟）

### Slide 13｜产品核心定位与闭环：从接入到复测，只走一条路（`one-loop-onboarding-to-retest`｜约 40 秒）

openOutcry 的定位，是一个**面向中国 A 股投资 Agent 的评估与迭代环境**。它不是股票荐股服务，也不会向真实券商提交订单。

我们希望用户能够按这样的流程使用产品：选择或接入 Agent，配置一项实验，让它在历史信息条件下运行，检查决策、订单与账户变化，再修改配置，开展一次可比较的实验。

这里的**“训练”**，指的是配置调整、实验运行和结果复盘的过程，**并不意味着系统能够自动微调模型权重**。

### Slide 14｜三个相互连接的工作区：工作室、训练场与复盘（`three-workspaces`｜约 50 秒）

我把整个用户体验组织成三个相互连接的工作区。

在 **Agent 工作室（Agent Studio）**里，用户选择 Agent，并设置它的角色、工具、模型和风险偏好。每个配置版本都应该清楚地标识出这次究竟在测试什么。

在 **训练场（Arena）**里，用户能够同时看到 Agent 的决策事件流和模拟投资组合。我们的目标是把 Agent 说了什么，与订单如何变化、账户发生了什么、组合出现什么结果联系起来。

在 **复盘（Review）**里，用户检查决策过程、投资组合结果，以及不同运行之间可能存在的差异。

这不是三个彼此无关的仪表盘。它们构成了一条反馈闭环：**配置、观察、复盘、再调整**。

### Slide 15｜系统架构与职责边界：Agent 做决策，平台管事实（`agent-decides-platform-owns-facts`｜约 1 分钟）

在拟定的系统架构中，我们将 Agent 与市场模拟器分离。

**Agent 适配器**负责连接不同的 Agent 运行环境。设计中，我们考虑使用 Agent Client Protocol，也就是 ACP，作为统一控制接口；另外通过基于 MCP 的工具层，将市场观察、历史证据和交易动作以结构化调用的形式提供给 Agent。

但在模拟时钟、规则校验、订单执行结果和账户余额这些事项上，**最终权威必须掌握在模拟器手里，而不是语言模型手里**。因为 Agent 说一句“我买入了 100 股”，并不等于一笔合法订单已经真实地在模拟环境中成交。

每一次运行还需要保留完整的事件轨迹：Agent 看到了什么、引用了哪些证据、提出了什么动作、是否有人为干预、订单是通过还是拒绝、投资组合如何变化。

需要说明的是，这里介绍的是**目标后端架构**，并不是说完整协议接入和交易引擎已经部署完成。

### Slide 16｜三项关键设计取舍：评估可信，取决于三道边界（`three-boundaries-of-trust`｜约 1 分 30 秒）

其中有三项设计尤其重要。

**第一，时点信息约束（Point-in-Time）。** 在历史实验中，Agent 只能访问模拟日期当时已经可用的信息。否则，未来才发布的公告或后来修订的财报可能泄漏到过去，让评估结果产生误导。因此，规划中的研究网关需要根据模拟时钟，校验证据是否已经可以使用。

**第二，A 股交易规则。** 模拟引擎必须理解 T+1 卖出限制、停牌、涨跌停、交易手数、可用资金和交易费用等约束。提出交易和真正成交，是两种不同的事件。

**第三，人工介入与可复现性。** 如果用户修改了订单，记录就必须标明这是一笔有人为干预的交易。如果用户修改 Agent 后重新运行，数据区间、初始资金和其他条件就应该尽可能一致。此外，播放一段已记录的历史轨迹，也必须与重新调用模型进行推理明确区分。

这些设计不是装饰性的功能，它们是在保护评估结果本身的意义。

这套设计有相当大的目标。因此，对第一学期的期末汇报来说，最重要的问题是：**目前究竟有哪些部分已经运行起来，哪些仍然是工程目标？** 接下来我会清楚地区分两者。

## 04 · 实现、演示与评估（Slide 17–21｜约 8 分钟，含约 3 分钟演示）

### Slide 17｜第一学期实现范围：Term 1 交付了什么？（`term1-what-shipped`｜约 55 秒）

第一学期，我最主要的交付成果，是一个**可以运行、可以交互的 openOutcry 网页原型**。它使用 React、TypeScript、Vite 和 React Router 构建。在接入可用于实际实验的模拟后端之前，我首先着重解决如何把完整的用户决策流程做得清晰、可理解、可交互。

代码中已经包含 Agent 选择、训练任务、运行工作台、账户信息、组合图表、决策事件，以及用于复盘的交互弹窗。我并没有把每个页面当成独立的静态效果图，而是通过一个中心状态机，让用户操作能够一致地改变当前运行状态及相关界面。

这里有一个必须强调的边界：当前原型使用的是**虚构示例公司、预设事件和模拟组合数值**。界面上展示的收益仅用于演示，**不是经过测量的 A 股投资表现，不是经过验证的历史回测结果，也不是外部真实 Agent 的运行成绩**。

### Slide 18｜工程细节：一笔订单，是四个不同事件（`one-order-four-events`｜约 1 分 5 秒）

我想重点介绍一个实现上的选择：一笔订单如何在不同状态之间推进。

一笔**订单提案**，首先只是交易意图。当用户批准或修改它时，订单才进入已提交状态；仅仅因为用户批准了订单，账户就立刻发生变化，这是不合理的。必须经过独立的模拟撮合动作之后，持仓和现金才会更新，同时系统追加一条事件记录。相反，如果用户拒绝订单，账户就应保持不变。

在当前原型中，这些状态变化通过基于 reducer 的运行状态机实现。事件流、持仓和组合统计都基于同一份底层状态，而不是由不同页面分别维护可能相互矛盾的数据副本。

这是一个有意义的**交互与领域模型原型**。不过，当前演示撮合中的成交价格和费用仍然写死在代码里。未来还需要使用真实历史数据，并由经过测试的执行引擎替换这些演示逻辑。

[展示新增事件、账户视图或复盘弹窗。如果最终版本不存在撮合按钮，则展示冻结的示例记录，不要宣称已经执行了对应操作。]

“最后，事件历史和投资组合视图让我们能够看到决策产生的影响。刚才的演示验证的是**界面工作流程**，并不能证明某项交易策略具有盈利能力，也不能证明历史交易引擎已经正确实现。”

### Slide 20｜证据边界：我们已验证交互，尚未验证收益（`verified-vs-unverified`｜约 1 分钟）

刚才的演示可以说明原型具备三项有价值的特征。

第一，多阶段决策能够被组织成一条清晰、易于理解的过程，而不是只显示一段聊天回答。第二，人工批准和拒绝可以被明确记录。第三，界面可以把订单状态、投资组合变化和事件历史联系起来。

但这**并不能证明**外部 Agent 已经能够自主完成交易决策，也不能证明完整的 A 股交易规则引擎已经运行，或者历史信息的时点约束已经得到验证。这些仍然需要后端接入和专门测试。

在学术答辩里，这个区别很重要：一个逻辑完整的交互界面，确实是项目进展；但它还不等于一个已经通过实验验证的评测平台。

### Slide 21｜验证计划与尚存差距：下一步，怎么证明它可信？（`how-to-prove-it-next`｜约 1 分 45 秒）

在软件工程层面，仓库已经配置了 TypeScript 检查、生产构建、单元测试和 UI 审查脚本，也包含对工具计算与派生状态的测试。这些为检查代码质量和交互一致性提供了方法。不过，如果没有最新一次测试的实际运行记录和输出，我不会宣称某个具体的通过数量或性能指标。

在下一阶段的评估中，我计划分四层开展验证。

**第一层，界面与状态转换。** 检查批准、修改、拒绝、模拟成交、任务切换、错误状态和账户约束。例如，一笔被拒绝的订单不应该改变可用资金。

**第二层，市场规则正确性。** 使用固定的历史数据集，对 T+1 约束、停牌、涨跌停、交易费用、持仓变化和投资组合计算进行测试，并与已知正确结果核对。

**第三层，时间信息完整性。** 人为放入一份发布时间晚于模拟日期的公告，检查 Agent 是否确实无法检索到它。这可以证明时点过滤是否真正生效，而不只是写在架构图里。

**第四层，受控对照实验。** 在相同数据和规则条件下多次运行，记录配置版本和人工介入情况，并区分确定性的轨迹回放与重新调用模型产生的随机性决策。只有到这一步，收益、回撤和横向比较图才具有可辩护的实验意义。

在当前阶段，后面这些测试仍属于**评估计划**，而不是已经完成的实证结果。这也是第一学期交付成果最主要的局限。

## 05 · 结论与后续工作（Slide 22–23｜约 1 分 30 秒）

### Slide 22｜总结与下期里程碑：让 Agent 先可测试，再谈可信（`testable-before-trustworthy`｜约 1 分 20 秒）

最后，我想用一个问题的转变来总结 openOutcry。我们不再只问：一个 Agent 能否给出有说服力的股票推荐？而是进一步问：用户能否**评估它连续做出的决策、理解这些决策的后果，并在可比较的条件下持续改进它**？

这一学期，我明确了产品需求，调研了 Agent 接入协议和市场模拟中的关键问题，设计了目标系统架构，并实现了一个交互式前端原型，用来展示预期的用户流程，以及订单提案、人工批准和模拟执行之间的区别。

这已经为未来的 Agent 评估环境打下基础，**但还不是一个已经完成的评估平台**。

下一阶段，我会优先通过选定协议接入 Agent，建立历史 A 股数据和交易模拟后端，实现符合模拟时点的信息访问控制，持久化保存完整事件轨迹，并在此基础上开展可复现的实验，计算明确的风险与绩效指标。

下一阶段最重要的里程碑，并不是把界面打磨得更漂亮，而是能够展示**一次完整且可核验的运行**，以及一次受控重跑，并清楚解释两次运行之间的差异。

### Slide 23｜致谢与问答：Thank you. Questions?（`closing-thank-you`｜约 10 秒）

归根结底，openOutcry 想做的，是让投资 Agent **先变得可测试，再谈是否值得信任**。

感谢各位老师的聆听。欢迎提问。
